- Data model is built up of *3 layers*
	- Conceptual data model
		- Which *information* is included in database
			- Lays basis for which tables and columns will be present
			- No technical details
			- Notation: *ERD* (Entity Relationship Diagram)
				- Building blocks
					- Entity types (rectangles)
						- *Concepts* that need to be described
						- Entity types
							- Collection of several *attributes*
							- Entity types without attributes are problematic and should be avoided
							- For example
								- lecturer, reservation, server
						- Entities
							- Actual examples
							- For example
								- Jan Van Hee, Bram Van Imple, Rudi Swennen
						- Notation
							- Rectangle containing the name of the attribute
							- Name is singular
							- Name starts with capital letter
						- How to recognise
							- Nouns
							- Has properties
							- Is not already a property of another entity type
					- Attributes (ovals)
						- *Properties* of *concepts* that need to be included in the database
						- Also referred to as *entities*
						- Multiple *attributes* are linked to one *entity type*
						- The *domain* describes the values an attribute can take
						- Key attributes
							- Combinations of attributes that is unique for every entity of an entity type
							- Often used to identity a certain entity
							- Terminology
								- Composite key
									- Key made up of *several* attributes
								- Natural key
									- Key that *has meaning* in the dataset
								- Technical key 
									- Key that *has no meaning* outside the dataset
							- Candidate keys
								- Every possible key of a table is considered a candidate key
								- A primary key is one of the *candidate keys* chosen to uniquely identify every row of a table
							- Notation
								- Same as normal attribute
								- Name is *underlined*
							- How to recognise
								- Same as normal attribute with one of the following
									- Unique and never empty for every entity
										- = natural non-composite key
									- Combination of as few attributes as possible that are unique and never empty for every entity
										- = natural composite key
									- If above two cannot be applied, add ID as attribute
										- = technical key
						- Notation
							- Oval containing the name of the attribute
							- Name is singular
							- Name starts with capital letter
							- An attribute is linked to *at most* 1 entity type
							- Attributes with the *same name* may occur with several different entity types
						- How to recognise
							- Nouns
							- Is a property of an entity type
							- Something we want to store in the database
					- Relationships (diamonds)
						- *Connections* between different *concepts*
				- Example

	- Logical data model
		- How data is *structured* according to *database model*
		- *Conceptual model* translated into the structure of the *database model*
		- Conceptual -> Logical
			- All *entity types* in the conceptual data model become tables in the logical data model
			- All *attributes* in the conceptual data model are listed in the table in the logical data model
			- *Key attributes* go at the top of the table, are marked with *PK* and are separated from the rest by a line.
		- Includes
			- Which tables will be created
			- Doesn't include data types
	- Physical data model
		- How the data structure is *described* according to chosen *DBMS*
		- From logical to physical
			- From tables to actual SQL code
		- Adding consistent naming
		- Adding technical details
			- *Data type* of columns
			- Maximum *length* of a value
			- Whether or not a value can be *empty/ NULL*
