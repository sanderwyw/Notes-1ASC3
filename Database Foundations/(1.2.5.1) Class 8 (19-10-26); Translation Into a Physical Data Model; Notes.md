- Physical Data Model
	- Depends on the chosen *DBMS* (database management system)
	- Adds *technical details*
		- Data types of columns
		- Maximum length of a value
		- Required or not
		- Restrictions/ constraints
		- There are more but they will not be covered in this course
- From Logical to Physical
	- 1. Give every column a *name* according to the naming conventions
		- Tables and columns
			- Singular
			- Lowercase
			- Separate words with underscore ( _ ) instead of space 
			- As short as possible, but not at the expense of clarity or readability
		- Primary keys
			- id (if possible)
		- Foreign key
			- XXX_id, where XXX refers to the original table of the foreign key
	- 2. Add *data types* and *maximum length*
		- Char
			- Used for a string of text that must be a certain length
			- More storage efficient than varchar
		- Varchar
			- Used for a string of text that cannot be longer than a length specified by the user
		- Integer
			- Used for numbers, can go up to incredibly high numbers
		- Smallint
			- Used for numbers, doesn't go up to very high numbers
			- More storage efficient than integer if only small numbers are used
		- Date
			- Used to store dates, and can be compared to other dates
	- 3. Indicate whether or not the value in a column may be *empty*/ *NULL*
		- Reasons for NULL
			- Value is (still) *unknown*
			- Column is *not applicable* for this entity
		- Figuring out whether a column could ever be empty can often be done by *reasoning* from the client's point of view
		- Primary keys can *never* be empty
		- Foreign keys can *sometimes* be empty, depending on the following criteria:
			- (1-1) or (1-N) relationships
				- Minimum cardinality 1 = *cannot* be empty
				- Maximum cardinality 0 = *can* be empty
			- (N-M) relationship
				- Can *never* be empty
