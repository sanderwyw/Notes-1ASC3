- Special Attributes
	- Derived Attributes
		- Attribute that can be *derived from* another attribute
		- Notation
			- Conceptual
				- Oval with a **dotted line** containing the name of the attribute
				- Name is singular and starts with capital letter
				- Attribute it is derived from is *not noted*
			- Logical
				- Derived attributes are *not noted* in the logical data model
		- Examples
			- Age from birthday
			- Date of birth from national register number
	- Multi-valued attributes
		- Attribute that can take *several values* for the same entity
		- Notation
			- Conceptual
				- Oval with **double solid line** containing the name of the attribute
				- Name is singular and starts with a capital letter
			- Logical
				- Create *separate table* for the multi-valued attribute
				- It has the *original* entity type id as primary key *and* foreign key
				- Each *attribute* also counts as a *primary key*, which is a composite key with the id
		- Examples
			- Languages someone speaks
			- Qualifications
			- Driving licenses
			- Nationalities
- Special Types
	- Generalisation
		- Bringing *together* the *common characteristics* of several entity types into *another* general entity type
			- Referred to as **supertype**
		- Overlapping vs disjoint
			- Overlapping
				- An entity of the supertype can be an entity of *several subtypes*
			- Disjoint
				- An entity of the supertype can be an entity of at most *one* subtype
		- Total vs optional
			- Total inheritance
				- An entity of the supertype *must* also *be an entity* of at least *one* of the *subtypes*
			- Optional inheritance
				- An entity of the supertype *may* be an *entity* of at least *one* of the *subtypes*
		- Notation
			- Conceptual
				- Draw a **line** connecting the supertype to a **circle**
					- If the connection is **optional**, the line is *singular*
					- If the connection is **singular**, the line is *double*
				- Draw the appropriate letter inside of the circle
					- If the connection is **disjointed** write a *D*
					- If the connection is **overlapping** write an *O*
				- Draw lines from the circle to each of the subtypes, with a semicircle in the middle of each
					- The semicircle's inside *faces the circle*
			- Logical
				- Method 1
					- Write the supertype and subtypes on *one table*
					- Use cases
						- Majority of the attributes are *common*/ *shared*
						- Common relationships have to be *attached*
						- *Inheritance* is overlapping and/or total
				- Method 2
					- Write the *subtypes* on several tables, each being connected to the *supertype*
					- Draw a connection line going *out of* the *supertype table*, which then *splits apart* into lines that are each connected to a distinct *subtype table* 
					- The *primary* key and *foreign* key for each *subtype table* are identical to the primary key of the *supertype table* 
	- Specialisation
		- *Dividing* a *general* entity type into several *more specific* entity types on the basis of *distinguishing* characteristics
			- Referred to as **subtypes**
	- Advantages
		- *Less redundancy* as each characteristic in modelled only *once*
		- Common relationships can be *attached to* the *general* entity type
		- Makes the common structure *explicit* and *clearer*
	- Disadvantages
		- More complex to *implement*
		- More complex to *change*
			- Changes to common characteristics can cause consequences for the subtypes 
- Special Relationships
	- Degree of the relationship
		- Binary
			- 2 entity types with 
		- Unary
			- Relationship between an entity *type* and *itself*
			- Notation
				- Conceptual
					- Draw a line connected to a relationship *diamond*, and then a line from that diamond *back* to the *relationship*
					- Cardinality must be written down for *both* lines
				- Logical
					- 1-1 or 1-N
						- Draw a line between the *primary* key of a table to a *foreign* key in that *same* table with the *name* of that relationship
						- Cardinality *must* be included in the relationship line
					- N-M
						- Create a *junction table* that goes back into the original table
			- Examples
				- A football coach who plays in the team himself
				- Family relationships
				- Workers coaching other workers
		- Tertiary
			- 3 entity types with eachother
			- Notation
				- Conceptual
					- The *best* and *simplest* way to write this down is to connect *all three* entity types to *one* relationship 
					- Cardinality should be decided by evaluating the entity type's relationship with both other entity types
				- Logical
					- Create table for all three entity types
					- Create a *junction table* for the ternary relationship
					- The cardinalities on the side of the entity types are always (1, 1)
					- The original cardinalities go on the side of the junction table
				- Physical
					- Translation into a physical model stays largely the same
			- Examples
				- **Doctors** *prescribes* **medication** for a **patient**
