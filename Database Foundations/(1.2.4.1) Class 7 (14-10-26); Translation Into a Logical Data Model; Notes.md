- Data model
	- *Visual* and *schematic* representation of the *data* included in the database
	- Conceptual data model
		- Similar to a *mind map*
		- *Attributes* (ovals) are attached to *entity types* (rectangles) with lines. Sometimes they are connected via a *relation* (diamond)
	- Logical data model
		- *Box* 
		- *Entity type* listed in rectangle at top of box
		- *Key type* listed in thin rectangle at the left
				- *Primary attributes* go at the top and are marked with 'PK', and a line is drawn under that section, creating another rectangle
		- *Attributes* listed in wide rectangle at the right
- Database model
	- *Structural* representation of the *database* and how the *data* is *organised* and *manipulated* within it.
	- Purpose of database models
		- Everyone in the industry can use the *same* standards that are *mutually understood*
			- Allows for developing *software* for said standards
		- The model can be *expanded upon* for different purposes. I.e. different *types* of data, different *needs* or differences in *storage capacity*
	- Relational Database Models
		- Principles
			- All data is contained in *tables* (like the ones from your SQL output)
				- *Attribute* = **column**
				- *Entity* = **row**
				- *Entity type* = **table**
			- Keys are used to create *connections* between tables (this part is very similar to the JOIN function)
				- Candidate key
					- All *possible* keys of a table
				- Primary key
					- One of the candidate keys that was *chosen* to uniquely identify every row (table) of a table
					- The value of this key will be unique for every entity of an entity type
				- Foreign key
					- *Primary key* of *another* table that is added to a *different* table to express the *connection* with that foreign key's *original* table
					- I think this is the column that we enter in the JOIN ON x SQL statement
		- Translating relationships
			- **Translating 1-1 relationships**
				- (0,1) to (1,1)
				- Each *entity* in entity type A has exactly *one* *counterpart* in entity type B
				- Example: person has ID card
				- Conceptual data model
					- Write (0, 1) and (1, 1) next to the connection of their entity types 
				- Logical data model
					- Add the primary key of table A to table B as a foreign key, drawing a line from the primary key to the new foreign key.
					- Crow's foot notation
						- If *maximum cardinality* is **0**, draw an **O** at the end of the line next to the entity type, instead drawing an **I** if the *maximum cardinality* is **1**
							- For this relationship type, maximum cardinality will *always* be 1.
							- For 1-N relationships it can be *either* 1 or N.
						- If *minimum cardinality* is **0**, draw an **O** at the end of the line, *next* to the notation of *maximum cardinality* on the side that is *further away* from the *entity type*
						- This notation is written next to the *receiving* entity type; the *opposite* side of normal cardinality notation
					- Guidelines
						- Foreign key on the side with minimum cardinality 1 (*x*, y)
						- Both the same: choose either one
			- Translating 1-N relationships
				- Each *entity* in entity type A *can* have *multiple counterparts* in entity type B
				- Example: Person buys car (he can buy one or multiple cars)
				- Conceptual data model
					- Write (1, N) and (0, 1) next to the connection of their entity entity types.
				- Logical data model
					- Refer to the steps in '**Translating 1-1 Relationships**' that I just covered as the steps are very similar and I'm not copying all that cause redundancy and word count
					- If *maximum cardinality* is **N**, write a '**crows foot**', written as ⟀ (where the middle line should align with the line between the two entity types and all three lines should touch the entity type)
			- Translating N-M relationships
				- Each *entity* in *both* entity type A and B *can* have *multiple counterparts* in the *other* entity type
				- Example: Student attends course (student can follow multiple courses and courses can be followed by multiple students)
				- Conceptual data model
					- Write (1, N) and (1, M) next to the connection of the entity data types
						- Normally both maximum cardinalities would be **N**, but because there is *already* one **N** the *other* is written as **M** instead.
					- N-M relationships are the only relationship type that can have their *own attributes*. 
						- Attributes are connected to a *relationship* represented by a **diamond**
						- The two related entity types are connected to the *relationship*, not *directly* to eachother
				- Logical data model
					- Create a *junction table* that represents the relationship (like the diamond in the conceptual data model)
						- This table should be called: "**tableA**|**verb**|**tableB**"
						- Add the PKs from the two related entity types to the junction table as "foreign keys" **FK1** and **FK2**
							- Foreign keys are *not* placed in a separate row like with primary keys
						- Add the *relationship attributes* underneath the *foreign keys*
					- Construct a *composite* primary key for the junction table
						- A certain *combination of attributes* in the junction table will give you a unique value for every row
					- Draw the *connection*/*relation lines* from the primary keys on the entity types to the primary keys on the junction table.
						- *Both* lines will have a *crow's foot* at the end
						- The crow's foot will *always* be connected to the junction table
