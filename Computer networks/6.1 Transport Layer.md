- Transportation of Data
	- Role
		- Maintaining logical communications between applications running on different hosts
		- Connecting the application layer and the lower layers
	- Responsibilities
		- Tracking individual conversations
		- **Segmenting** data and **reassembling** segments
		- Adds **header** information
		- **Identify**, **separate** and **manage** multiple conversations
			- A *conversation* refers to the exchange of information between a pair of programs
		- Uses **segmentation** and **multiplexing** to enable different communication conversations to be interleaved on the same network
	- Protocols
		- IP does **not** specify **how** the delivery or transportation of the packets takes place
		- Protocols specify **how** to transfer messages between hosts. They are responsible for maintaining the reliability requirements to uphold a *conversation*
		- Transmission Control Protocol *(TCP)*
			- TCP provides reliability and **flow control**
			- Operations
				- **Number** and **track** *data segments* transmitted to a specific host from a specific application
				- **Acknowledge** received data
				- **Retransmit** received data
				- **Sequence** data that might arrive in wrong order
				- **Send data** at an efficient rate that is acceptable by the receiver
				- Used when it is important that **all** the data arrives and that it can be **processed** in its proper sequence
				- Used as **transport protocol**
		- User Datagram Protocol *(UDP)*
			- Provides basic functions for **delivering** *datagrams* between applications
				- Datagram = connectionless data packet kinda
			- Very little overhead or data checking = best-effort
			- Connectionless
			- No acknowledgment that the data is received
			- Used when the data is **minimal** and retransmission can be done **quickly**
- TCP Overview
	- Features
		- Establishes a Session
			- *TCP* is a **connection-oriented** protocol that negotiates and establishes a **permanent** connection (or *session*) between source and destination devices **before** forwarding any traffic
		- Ensures Reliable Delivery
			- TCP **ensures** that each segment that is sent **arrives** at the destination and that none are lost along the way
		- Provides Same-Order Delivery
			- TCP **ensures** that each segment **arrives** in the **intended order** and that they aren't jumbled up
		- Supports Flow Control
			- When TCP is aware that the **network hosts'** resources are **overtaxed** it can request that the *sending application* **reduce** the rate of data flow
	- Header
		- TCP is a **stateful** protocol which means it keeps track of the **state** of the communication **session**
		- TCP records which information it has **sent**, and which information has been **acknowledged**
		- Header Fields
			- Source port
				- 16-bit field
			- Destination port
				- 16-bit field
			- Sequence number
				- 32-bit field used for data reassembly
			- Acknowledgment number
				- 32-bit field used to indicate that data has been **received** and that the **next byte** is **expected** from source
			- Header Length
				- A 4-bit field known as "data offset" that indicates the length of the TCP segment header
			- Reserved
				- A 6-bit field that is reserved for **future use** *?*
			- Control bits
				- A 6-bit field that includes *flags* which indicate the **purpose** and **function** of the *TCP segment*
			- Window size
				- A 16-bit field used to indicate the **number of bytes** that can be accepted at a time
			- Checksum
				- A 16-bit field used for **error checking** of the segment header and data
			- Urgent
				- A 16-bit field used to indicate if the contained data is **urgent**
- UDP Overview
	- Features
		- Data is **reconstructed** in the order that it is **received**
		- Any segments that are lost are **not** resent
		- There is **no session** establishment
		- Sender is **not informed** about resource **availability**
	- Header
		- Source port
			- 16-bit field used to identify the **source** application by **port number**
		- Destination port
			- 16-bit field used to identify the **destination** application by **port number**
		- Length
			- 16-bit field that indicates the length of **UDP datagram header**
		- Checksum
			- 16-bit field used for **error checking** of the datagram **header** and **data**
	- Use cases
		- Live video and multimedia applications
			- Can tolerate some data loss but require little to no delay
		- Simple request and reply applications
			- Where host sends request and may or not receive reply
			- DNS and DHCP
		- Applications that handle reliability themselves
			- Unidirectional communications where flow control, error detection, acknowledgments and error recovery is not required
			- SNMP and TFTP
- Port Numbers
	- Multiple Separate Communications
		- TCP and UDP transport layer protocols use **port numbers** to manage multiple, simultaneous conversations
	- Socket Pairs
		- Source and destination ports are placed within **segment**
		- **Segments** are then **encapsulated** within an **IP packet**
		- Combination of IP address and port number of same device is known as a *socket*
		- Sockets enable multiple processes to distinguish themselves from eachother

- TCP Communication Process
	- Server Processes
		- Each **application** process running on a **server** is configured to use a **port number**
			- Server cannot have **two** services assigned to the **same** port number within the same transport layer services
			- An active server application assigned to a specific port is considered **open**, which means that the transport layer **accepts** and **processes** segments addressed to that port
			- An incoming client request addressed to the correct socket is accepted
	- TCP Connection Establishment
		- Step 1
			- Initiating clients request a client-to-server communication session with the server
		- Step 2
			- Server acknowledges the client-to-server communication session and requests a server-to-client communication session
		- Step 3
			- Initiating client acknowledges server-to-client communication session
	- TCP Session Termination
		- Step 1
			- When client has **no more data** to send it sends a segment with the **FIN flag set**
		- Step 2
			- Server sends back an ACK to acknowledge the receipt of the FIN to terminate the session from client to server
	- TCP Three-Way Handshake Analysis
		- Functions of the Three-Way Handshake
			- Establishes that the **destination** device is **present** on the network
			- Verifies that the **destination** device has an **active service** and is **accepting requests** on the destination port number that the initiating client intends to use
			- **Informs** the destination device that the **source client** intends to establish a **communication session** on that port number
		- After the communication is **completed** the *sessions* are **closed** and the *connection* is **terminated**. 
		- Six control bit flags
			- URG
				- Urgent pointer field significant
			- ACK
				- Acknowledgment flag used in connection establishment and session termination
			- PSH
				- Push function
			- RST
				- Reset the connection when an error or timeout occurs
			- SYN
				- Synchronize sequence numbers used in connection establishment
			- FIN
				- No more data from sender and used in session termination
- Reliability and Flow Control
	- Reliability
		- Guaranteed and Ordered Delivery
			- TCP can help maintain **flow** of packets so that devices do not become **overloaded**
			- There may be times when *TCP segments* do not arrive at their destination or out of order
			- **All** data must be received and they must be **reassembled** into the original order
			- *Sequence* numbers are assigned in the *header* of each packet to achieve this
		- Data Loss and Retransmission
			- TCP provides methods of **managing** *segment* losses
				- Retransmitting *segments* for unacknowledged data
			- Most OS' employ an optional *TCP* feature called *selective acknowledgment (SACK)* which is negotiated during **three-way handshake**
				- If both hosts support *SACK*, the **receiver** can explicitly acknowledge which *segments* were received including any **discontinuous** *segments*
	- Flow Control
		- Window Size and Acknowledgments
			- *Flow control* is the **amount** of **data** that the destination can **receive** reliably
			- *Flow control* helps maintain **reliability** of *TCP* transmission by adjusting the **rate of data flow** for a given *session*
		- Maximum Segment Size
			- *Maximum Segment Size (MSS)* is the **maximum** amount of **data** that the *destination device* can **receive**
			- Common IPv4 MSS = 1460 bytes
			- *Ethernet maximum transmission unit (MTU)* is 1500 bytes (by default)
				- A host determines value of *MSS* by subtracting bytes of *IP* and *TCP* headers from *MTU* = 1460 bytes
		- Congestion Avoidance
			- When congestion occurs on a network, it results in packets being **discarded** by the **overloaded** router
			- TCP employs several congestion handling mechanisms, timers and algorithms
- UDP Communication
	- Low Overhead versus Reliability
		- *UDP* does not establish a connection **before** sending data
		- *UDP* provides **low overhead** data transport because it has a small **datagram** header and no network management traffic
	- Datagram Reassembly
		- Does **not** track *sequence numbers* the way *TCP* does
		- Has **no way** to **reorder** the datagrams into their transmission **order**
		- Simply **reassembles** data in the order that it was **received** and then forwards it
	- Server Processes and Requests
		- *UDP-based* server applications are assigned **well-known** or **registered** port numbers
			- UDP receives a *datagram* destined for one of these ports
			- Forwards application data to receiver based of its **port number**
