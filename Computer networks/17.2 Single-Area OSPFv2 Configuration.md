- OSPF Router ID
	- OSPF Reference Topology
		- Exercises with OSPFv2 will include the following:
			- Routers in the topology have a starting configuration, including interface addresses
			- Routers have no static routing or dynamic routing configured on them
			- All interfaces on R1, R2 and R3 (except loopback 1 on R2) are within the OSPF backbone area
			- The ISP router is used as a gateway to the internet of the routing domain
	- Router Configuration Mode for OSPF
		- Use *router ospf (process-id)* to enable OSPFv2
			- *process-id* represents a number between 1 and 65535 and is selected by the network administrator
				- *process-id* value is locally significant
				- It is considered best practice to use the same *process-id* on all OSPF routers
	- Router IDs
		- An OSPF router ID is a **32-bit value**, represented by an **IPv4 address**
			- It is used to uniquely identify an OSPF router
			- All OSPF packets include the **router ID** of the **originating router**
		- Every router requires a **router ID** to **participate** in an **OSPF domain**
			- It can be defined by an administrator or automatically assigned by the router
		- The router ID is used by an OSPF-enabled router to do the following
			- Participate in the synchronization of OSPF databases
				- During the Exchange State, the router with the **highest** router ID will **send** their **database descriptor** (DBD) packets **first**
			- Participate in the election of the designated (DR)
				- In a multiaccess LAN environment, the router with the **highest** router ID is elected the **DR**
				- The router with the **second highest** router ID is elected the **backup designated router** (BDR)
	- Router ID Order of Precedence
		- Cisco routers derive the **router ID** based on one of three **criteria** in the following order
			- 1.
				- The router ID is explicitly configured using the OSPF *router-id (rid)* router configuration mode command
				- This is the **recommended method** to assign a router ID
			- 2.
				- The router chooses the **highest IPv4 address** of any **configured loopback interfaces**
			- 3.
				- The router chooses the **highest active IPv4** address of any of its **physical interfaces**
		- Flow chart
			- Router ID explicitly configured?
				- Yes
					- Use that as the router ID
				- No
					- IPv4 loopback interface configured
						- Yes
							- Use that as the router ID
						- No
							- Use the highest active configured IPv4
	- Configuring a Loopback Interface as the Router ID
		- Instead of relying on **physical interfaces**, the **router ID** can be assigned to a **loopback interfaces**
		- Typically, the IPv4 address for this type of loopback interface should be configured using a 32-bit subnet mask (255.255.255.255)
			- This effectively creates a host route
			- A 32-bit host route would not get advertised as a route to other OSPF routers
			- Use *ip address 1.1.1.1 255.255.255.255*
		- OSPF does not need to be enabled on an interface for that interface to be chosen as the router ID
	- Explicitly Configuring a Router ID
		- In the reference topology the router ID for each router is assigned as follows
			- **R1** uses router ID **1.1.1.1**
			- **R2** uses router ID **2.2.2.2**
			- **R3** uses router ID **3.3.3.3**
		- Use the *router-id (rid)* router config mode command to manually assign a router ID
			- In the example, the router ID 1.1.1.1 is assigned to R1
		- Use *show ip protocols* to verify the router ID
	- Modify a Router ID
		- After a router **selects** a **router ID**, an active OSPF router does **not** allow the router ID to be **changed** until the router is **reloaded** or the OSPF process is **reset**
- Point-to-Point OSPF Networks
	- Network Command Syntax
		- You can specify the interfaces that belong to a **point-to-point** network by configuring the *network* command
			- You can also configure OSPF directly on the interface with the *ip ospf* command
		- The basic syntax for the *syntax* command is as follows
			- *Router(config-router)# network (network-address) (wildcard-mask) area (area-id)*
		- The *(netword-address) (wildcard-mask)* part of the syntax is used to enable OSPF on interfaces
			- Any **interfaces** on a **router** that match this part of the command are **enabled** to **send and receive** OSPF packets
		- The *area (area-id)* part of the syntax refers to the OSPF area
			- When configuring single-area OSPFv2, the *network* command must be configured with the same *area-id* value on all routers
			- Although any **area ID** can be used, it is good practice to use an area ID of **0**  with single-area OSPFv2
				- This makes it easier if the network is later altered to support multiarea OSPFv2

	- Configuring OSPF Using the network Command
		- Within **routing configuration mode**, there are two ways to **identify** the **interfaces** that will **participate** in the **OSPFv2 routing process**
			- 1.
				- The wildcard mask identifies the interface based on the network addresses
				- **Any** active interface that is configured with an IPv4 address belonging to that network will participate in the OSPFv2 routing process
				- Examples
						- *network 10.10.1.1 0.0.0.255 area 0*
						- *network 10.1.1.5 0.0.0.3 area 0*
			- 2.
				- As an alternative, OSPFv2 can be enabled by specifying the exact interface IPv4 address using a quad zero wildcard mask
					- Entering *network 10.1.1.5 0.0.0.0 area 0* on R1 tells the router to enable **only** interface Gigabit Ethernet 0/0/0 for the routing process
				- The **advantage** of specifying the interface is that the wildcard mask calculation is **not necessary**
				- Examples
						- *network 10.10.1.1 0.0.0.0 area 0*
						- *network 10.1.1.5 0.0.0.0 area 0*
	- Configuring OSPF Using the ip ospf Command
		- Use the *ip ospf* to configure OSPF directly on the interface
		- The syntax is as follows
			- *ip ospf (process-id) area (area-id)*
	- Passive Interface
		- By default, **OSPF messages** are forwarded out of **all** OSPF-enabled devices
			- However, these messages only need to be sent out interfaces that are **connecting** to **other** OSPF-enabled routers
		- Sending out unneeded messages on a LAN affects the network in three ways
			- Inefficient Use of Bandwidth
				- Available bandwidth is **consumed** transporting **unnecessary** messages
			- Inefficient Use of Resources
				- All devices on the LAN must **process** and **eventually discard** the message
			- Increased Security Risk
				- Without additional OSPF security configurations, OSPF messages can be **intercepted** with packet sniffing software
				- Routing **updates** can be **modified** and sent back to the router, **corrupting** the **routing table** with false metrics that may misdirect traffic
	- Configure Passive Interfaces
		- Use the *passive-interface* router configuration mode command to prevent the transmission of routing messages through a router interface, but still allow that networks to be advertised to other routers
		- Use *show ip protocols* command to verify that the interface is listed as passive
	- OSPF Point-to-Point Networks
		- Routers elect a DR and BDR on Ethernet interfaces, even if there is only **one other device** on the link
			- You can verify this with the *show ip ospf interface* command
		- The DR/BDR election process is **unnecessary** as there can only be **two** routers on the **point-to-point** network between **R1** and **R2**
		- Notice in the output that the router has designated the network type as BROADCAST
			- To change this to a point-to-point network, use the *op ospf network point to point* on all interfaces where you want to disable the DR/DBR election process
	- Loopbacks and Point-to-Point Networks
		- Use loopbacks to provide additional interfaces for a variety of purposes
			- By default, loopback interfaces are advertised as /32 host routes
		- To simulate a real LAN the loopback interface can be configured as a point-to-point network to advertise the full network
- Multiaccess OSPF Networks
	- OSPF Designated Router
		- In multiaccess networks, OSPF elects a **DR** and a **BDR**
		- Designated Router (DR)
			- The DR is responsible for **collecting** and **distributing** LSAs sent and received
			- The DR uses the IPv4 address *224.0.0.5* for multicasting which is meant for **all** OSPF routers
		- Backup Designated Router (BDR)
			- The **BDR** is elected in case the **DR** fails
			- **BDR** listens passively and maintains a relationship with all the routers
			- If the **DR** stops producing LSA packets, the **BDR** promotes itself and assumes the role of **DR**
		- DROTHER
			- A router that is neither the DR nor the BDR
			- DROTHER's use *224.0.0.6* for multicasting to send OSPF packets to **only** the **DR** and the **BDR**
			- Only the **DR** and **BDR** listen for *224.0.0.6.*
	- OSPF Multiaccess Reference Topology
		- In the multiaccess topology used throughout this document from this point onward, the following applies:
			- Routers
				- R1
					- RID: 1.1.1.1
					- IPv4: 172.16.1.0/24
					- Port to router: g0/0/0
				- R2
					- RID: 2.2.2.2
					- IPv4: 172.16.2.9/24
					- Port to router: g0/0/0
				- R3
					- RID: 3.3.3.3
					- IPv4: 172.16.3.0/24
					- Port to router: g0/0/0
				- Router
			- There are **three** routers interconnected over a common Ethernet multiaccess network
			- The routers are connected over a common multiaccess network
				- Because of this, OSPF has automatically elected a **DR** and a **BDR**
			- **R3** has been elected as **DR** because its router ID is 3.3.3.3 which is the highest in the network
			- **R2** has been elected as **BDR** because its router ID is 2.2.2.2 which is the second highest in the network
	- Verify DR/BDR Adjacencies
		- Use *show ip ospf neighbor* to show info about neighbors, and that **R2** has adjacencies with **R1** and **R3**
	- The ip ospf priority Command
		- If the interface priorities are equal on all routers, the router with the highest router ID is elected the DR
		- Instead of relying on the router ID, it is better to control the election by setting **interface priorities**. This also allows a router to be the DR in one network and a DROTHER in another
		- To set the priority of an interface, use the command *ip ospf priority (value)*, where value is any number 0 to 255
			- A value of 0 cannot become a DR or BDR
			- A value of 1 to 255 on the interface makes it more likely that the router becomes the DR or the BDR
- Modify Single-Area OSPFv2
	- OSPF Accumulates Cost
		- The **cost** of an OSPF route is the **accumulated value** from one router to the destination network
		- Assuming the the *auto-cost reference-bandwidth 10000* command has been configured on all three routers, the cost of the links between each router is now 10
			- The loopback interfaces have a default cost of 1
		- Example
			- The cost for R1 to reach R2 is 11, because the link to R2's cost = 10 and the loopback cost = 1
		- Use *show ip route (network address)*
	- Cisco OSPF Cost Metric
		- The table below shows the OSPF cost if the reference bandwidth is adjusted to accommodate 10 Gigabit Ethernet links. 
			- 10 Gigabit Ethernet 10 Gbps
				- 10.000.000.000 (Reference Bandwidth in bps) / 10.000.000.000 (Default Bandwidth in bps)
				- = Cost 1
			- Gigabit Ethernet 1 Gbps
				- 10.000.000.000 (Reference Bandwidth in bps) / 1.000.000.000
				- = Cost 10
			- Fast Ethernet 100 Gbps
				- 10.000.000.000 (Reference Bandwidth in bps) / 100.000.000
				- = Cost 100
			- Ethernet 10 Mbps
				- 10.000.000.000 (Reference Bandwidth in bps) / 10.000.000
				- = Cost 1000
		- The reference bandwidth should be adjusted anytime there are links faster than FastEthernet (100 Mbps)
		- Whichever method is used, it is important to apply the configuration to all routers in the OSPF routing domain
	- Manually Set OSPF Cost Value
		- Reasons to manually set the cost value 
			- By influencing path selection within OSPF, different paths can be selected than what normally would given default costs and cost accumulation
			- Connections to equipment from other vendors who use a different formula to calculate OSPF cost
		- To change the cost value reported by the local OSPF router to other OSPF routers, use the interface configuration command *ip ospf cost (value)*
	- Modifying OSPFv2 Intervals
		- It may be desirable to change the OSPF hello-timers so that routers detect network failures in less time
			- Increases traffic, although is sometimes preferable
			- Default Hello and Dead intervals should only be altered in rare situations
		- Use *ip ospf hello-interval (seconds)* to manually modify the hello interval
		- Use *ip ospf dead-interval (seconds)* to manually modify the dead interval
			- Dead interval means how long the router waits before declaring a neighbor dead
			- Dead interval is usually four times as much as Hello interval
- Default Route Propagation
	- Propagate Default Static Route in OSPFv2
		- To propagate a default route, the edge router must be configured with the following
			- A **default static route** using the *ip route 0.0.0.0 0.0.0.0 [next-hop-address | exit-inf]* command
			- The *default-information originate* router configuration command
				- This instruct **R2** to be the source of the default route information and propagate the default static route in OSPF updates
		- In the example, R2 is configured with a loopback to simulate a connection to the internet
			- A default route is configured and propagated to all other OSPF routers in the routing domain
	- You can verify the default route settings on **R2** using the *show ip route* command
		- With this, you can also verify that **R1** and **R3** received a default route
	- The route source should say **O * E2**, signifying that it was learned using OSPFv2
		- The asterisk identifies this as a good candidate for the default route

			- *show ip ospf neighbor*
				- Use this to verify that the router has formed an adjacency with its neighboring routers
				- If the router ID of the neighboring router is not displayed or is not in a state of FULL, the two routers have not formed an OSPFv2 adjacency
					- A non-DR or BDR router that has a neighbor relationship with another non-DR or BDR router will display a two-way adjacency instead of full
					- If they have not formed an OSPFv2 adjacency, one of the following phenomena has occurred
						- The subnet masks do not match, causing the routers to be on separate networks
						- The OSPFv2 Hello or Dead timers do not match
						- The OSPFv2 Network Types do not match
						- There is a missing or incorrect OSPFv2 network command

			- *show ip ospf*
			- *show ip ospf interface*
